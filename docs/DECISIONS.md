- 2026-07-17 — **Apple-light rebuild: palette = official brand ramp, not the brief's invented values.** The brief proposed green `#0d7a43` + orange `#e0561f`; `#e0561f` computes to **3.80:1** with a white label and fails the brief's own ≥4.5:1 bar. `globals.css` §1 already ships the Pishon ramps, whose darker steps pass harder. Client approved: **Ember-600 `#ad4527`** (5.74:1) = the single orange fill, **Ember-700 `#8c3820`** (7.77:1) = orange text-links. Avoids inventing a third green/orange and keeps "brand untouched" literally true. Apple's own `#86868b` is also banned (3.62:1); `#6e6e73` (5.07:1) is the Apple-authentic value that passes.
- 2026-07-17 — **Green ink = Forest-500 `#2d5d49` (~7.6:1), not Forest-600 `#20493b` (10.11:1).** Caught from the Phase 2 screenshots, not the contrast table: Forest-600 passes AAA but at eyebrow/rule sizes on white it reads as near-black, so the green accent stops registering as green. Forest-500 still clears AA comfortably while actually reading green. Forest-400 `#4c7a63` (4.92:1) was rejected — only 0.42 above the floor. — Contrast math alone can't tell you whether a colour *reads* as itself; the ratio was never the whole question.
- 2026-07-17 — **Type = Candidate A, "Inter Display + Inter" (client pick at the Phase 2 STOP).** Implementation note: **Inter Display is not a Google Fonts family.** Inter carries an `opsz` axis (14–32) and Inter Display *is* Inter at display optical size, so the pairing ships as one variable family at two optical sizes: `next/font/google` requests `axes: ["opsz"]`, and `.text-display/.text-h1/.text-h2/.font-display` pin `font-variation-settings: "opsz" 32`. Body text optically sizes itself. Rejected: B (Instrument Sans), C (Schibsted Grotesk + Inter — headline wrapped to 3 lines at 1440 where A took 2). Sora + Figtree retired. JetBrains Mono survives on borrowed time until Phase 3 retires the mono-uppercase eyebrow idiom.
- 2026-07-17 — **`position: fixed` is unreliable inside page content, sitewide.** `template.tsx` wraps every route in `.route-enter`, whose entrance animation holds a `transform` for its duration; a transformed ancestor becomes the containing block for `position: fixed` descendants, collapsing an `inset: 0` overlay to 0px. Existing fixed elements (WhatsApp widget, cookie consent) are unaffected only because they live in `layout.tsx`, *outside* the template. — **Load-bearing for Phase 3:** the sticky-storytelling pin and any lenis-driven fixed positioning live in content and will hit this. Prefer `position: sticky` (unaffected) or hoist to the layout.
- 2026-07-17 — **Two tones only: white canvas + `#f5f5f7` band. `inverse` deleted, not aliased.** Apple's rhythm is two-tone; green is ink, never canvas. After the light flip `--brand` and `--surface` both resolved to `#f5f5f7`, so `Section tone="inverse"` and `tone="muted"` rendered **identically** — a third code path emitting a second tone's pixels. Aliasing would have kept the dead path alive, so the tone is gone from both `Section` and `CTABand`; TypeScript then named all four call sites and now enforces the two-tone rule at compile time. `raised` survives as white-plus-hairline (a variant of the canvas, not a third colour). Knock-on: `CTABand`'s default tone moved `inverse` → `surface`, which flips `onColor` and swaps `opacity-85` for `text-muted` on every band — an improvement, since alpha-on-text is the failure species we swept sitewide. — Client call, 2026-07-17.
- 2026-07-17 — **Section alternation is enforced per page; the same-tone collapse is the fallback, not the fix.** `/about` stacked three consecutive white sections into a 439px void. Primary fix: alternate the bands (hero white → prose/image band `#f5f5f7` → white). The collapse rule (adjacent same-tone sections step DOWN the scale: 80→48, 128→80, 160→96) stays as the systemic backstop for pages where alternation doesn't fit. Collapsed values step down the approved scale rather than taking a raw 40% (128×0.6 = 76.8px would put sections off-scale and fail the conformance gate). The rule is deliberately **unlayered** — Tailwind's utilities layer beats `@layer components` regardless of specificity, the same cascade trap that made `.reveal-rule`'s width beat `w-10`.
- 2026-07-17 — **Motion diagnosis (#5, "the client cannot see the motion"): it's a BUG, not subtlety. Named, not yet fixed.** Measured in a production build, real Chromium, `prefers-reduced-motion` explicitly OFF: the first `.reveal-init` on home already carries `.reveal-in` at t+0 — opacity 1, transform none, **zero animations**, sampled every 60ms for 600ms. It never animates. **Cause:** `public/reveal.js` sets `html.reveal-ready` at `beforeInteractive`, then `setup()` synchronously adds `.reveal-in` to every element already in view. Both land before first paint, so the browser never paints the hidden start state and there is nothing to transition *from* — the element just appears. **Everything above the fold is silently static, which is the entire first impression.** Below-the-fold reveals are fine (the IntersectionObserver fires long after first paint) — which is exactly why scroll-reveal always looked right and nobody noticed the hero. Verified on the committed code: 26 of 34 `.reveal-init` are correctly still hidden 1.5s after load, awaiting scroll; under reduced motion 0 are hidden, so the "never stuck hidden" guarantee holds. **Do NOT amplify durations/distances until this is fixed** — the values were never the problem; tuning them would change nothing above the fold and would over-animate everything below it. **A naive double-rAF fix was tried and REVERTED**: it regressed reduced-motion to opacity 0 (content invisible for the users who most need it), which the CSS at `globals.css` §reveal says should be impossible — meaning the interaction between the script's timing and the reduce rules isn't yet understood. The next pass must explain that contradiction before shipping, not work around it.
- 2026-07-17 — **Motion bug FIXED (follow-up to the diagnosis above).** Confirmed the mechanism the client hypothesised: the base hide (`opacity:0`) and the reduce override (`opacity:1`) have identical specificity `(0,3,1)`, so the override won **only on emission order** in the compiled CSS. Correct today, one Tailwind layer re-sort from silently hiding content from reduced-motion users. Fix per the approved shape: (1) `reveal.js` now gates on `matchMedia("(prefers-reduced-motion: reduce)")` and returns before adding `reveal-ready` — under reduce the hidden rule's `html.reveal-ready` ancestor never matches, so content is unconditionally visible and we no longer DEPEND on the CSS tie (kept as defense-in-depth). (2) Above-the-fold `.reveal-init` elements now get `reveal-in` after a double-rAF, so the hidden state paints once and the entrance actually transitions. **Verified with an init-script rAF sampler (the coarse post-hoc sampler lied both ways):** no-preference above-fold ramps opacity 0→1 over ~450ms; reduce holds opacity 1 the entire time (min opacity 1.0, never hidden). The earlier reverted double-rAF attempt "regressed" reduce only in a mis-timed measurement — the real code path is clean. **Entrance VALUES were never the problem** (already 16px/0.65s, top of the client's target range), so amplification is re-evaluated separately, not assumed.
